# `ci-ty` — CI green against the latest ty

## Summary

Every master CI run since 2026-10-06 failed at `uvx ty check src` and skipped the rest of the `checks` job (the `slow` job was green). `uvx ty` resolves the *latest* ty on each run — 0.0.88 at the time — whose new rules flag seven overrides that ty 0.0.84 (the version the project was verified against, ADR-0004) accepted. The seven sites are made clean under both versions, CI is pinned to *latest on purpose* (`uvx ty@latest`, so a cached older build cannot mask a new rule), and ty joins the dev group for a reproducible local `uv run ty check src`.

## Design

- Validate against the latest ty rather than a pin (Joon, 2026-10-15): the checker is in active development and the rules it adds have so far been correct (the properties *were* ADR-0004 violations). The price is an occasional red CI after a ty release, repaired by `uv lock --upgrade-package ty` locally and a fix-forward. *Rejected*: pinning ty in CI (hides new rules until someone remembers to bump).
- `uvx ty@latest` rather than `uvx ty`: uv caches tool environments, and with `setup-uv`'s cache enabled a plain `uvx ty` can serve an older build; `@latest` forces a resolve.
- Templates' `raw` annotation: `None` was the honest type (a template's `raw` is always `None`), but a subclass may not narrow a mutable attribute (Liskov; ty's `invalid-mutable-override`). The base annotation with `default=None` costs nothing at runtime — the field is static, `init=False`, and `_init_raw` is never called on these classes.
