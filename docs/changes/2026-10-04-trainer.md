# `trainer` — Phase C: the training loop, losses, schedules, evaluation, checkpoints

## Summary

The trainer becomes a small pure core with injected side effects (ADR-0009): `Trainer`
defines a jitted `train_step`, `TrainerState` holds everything that changes (now
including the loss-weight schedule's state), and `train()` takes a logger, a
checkpointer and an evaluation function. Losses are weighted sums of named terms whose
weights the trainer's schedule supplies each step — constant, curriculum, or Yawata et
al.'s once-and-for-all threshold switch. Validation is a fixed set of held-out windows
evaluated through the `AbstractPhaseAmplitudeModel` contract (`val/mse` selects the best
checkpoint; the learned period, κ, the bijection's round trip and Jacobian singular
values on the data's bounding box, and — when the data come from a normal form — the
phase and amplitude agreement with the exact chart). Orbax checkpoints save the whole
state and resume. The one-step-delayed logging survives as a `DelayedLogger` adapter.
`scripts/training/` is deleted (Phase D rebuilds it).

## Review round 1 (2026-10-04) — what changed in response

- **The loader owns the device transfer.** `train` no longer calls `to_device`; the
  trainer uses batches as yielded. `data.to_device(dataset, device, cpu_buffer_size,
  device_buffer_size)` wraps `grain.experimental.device_put` — the tutorial's option C
  ("`ThreadPrefetch -> map(jax.device_put) -> ThreadPrefetch`", "the recommended pattern
  for real training") — and the notebook uses it. NumPy batches still work (`jit`
  transfers them synchronously), which is what the tests do. This also covers most of C7:
  the CPU-side thread hides the window slicing whenever a step is longer than it.
- **Validation as a finite, deterministic dataset.** `validation_windows(source, length,
  stride)` enumerates every window at fixed starts of every held-out trajectory, in order,
  without shuffle or repeat; `Evaluator(val_data)` iterates it to exhaustion on every call
  (levanter's eval loop), accumulating sufficient statistics per batch — weighted sums for
  the MSEs, `Σ exp(iΔ)` for both orientations and second moments for the amplitude
  correlation — so nothing is held in memory and the bounding-box grid is taken from a
  first pass. Why not stream from the training-style loader: it is infinite and shuffled,
  so each evaluation would see different windows and `BestN` would select on noise.
  `collect_batches` stays as a convenience; the slow test and the notebook use
  `validation_windows`.
- **Context managers.** `Logger` and `Checkpointer` gain `__enter__`/`__exit__` (exit
  closes); `train` does `with log, ckpt:`, so the `DelayedLogger` flushes even when a
  step raises. (`typing.Self` is avoided in the protocols: the beartype import hook
  rejects it outside `@beartype` classes, as it did in `trainer.py` before.)
- **`terms -> (terms, aux)`.** `terms` must be exactly the weighted set (`__call__`
  raises otherwise; `__check_init__` checks `default_weights` against `weight_names`),
  `aux` holds diagnostics. `ConjugacyTrajectoryLoss`: terms `data`, `latent`; aux
  `final` (kept as a diagnostic — the error at the window's end exposes a frequency drift
  the mean hides). `PhaseAutoencoderLoss`: aux `omega`, `kappa`.
- **Typed schedule state.** `AbstractLossSchedule[S]`; `Constant`/`StepSchedule` are
  `[None]`, `ThresholdSwitch` is `[Bool[Array, ""]]`; docstrings name the state.
- **`circular_std`, justified** in `phase_amplitude_agreement`'s docstring and ADR-0009:
  offset invariance, wrap safety, and equality with the ordinary standard deviation for
  small spread (Mardia & Jupp 1999, as cited by SciPy's `circstd`).
- **American English.** 145 British spellings converted across `src`, `tests` and `docs`
  (`normalise_phase_plane` → `normalize_phase_plane`), the "centerd" typo from the
  search-and-replace fixed, and the rule added to `CLAUDE.md`.
- Hypothesis found a fragile assertion in `test_encoder_normalization` while the suite
  ran (`y = (−1, 2e−311, 0)`: `arctan2` lands on `±π` either side of normalization); the
  angle is now compared modulo 2π.

## Review round 2, part 1 (2026-10-04) — the benchmark and what it exposed

Joon's second V100 run was reproducibly inconsistent (device-resident batches 644 ms per
step, NumPy batches 90 ms, `to_device` 418 ms): a lower bound above the worst case means
the step column measured something other than the steady-state step. Changes:

- **`scripts/bench_dataloader.py` redesigned**: `--device` is required (index into
  `jax.devices()`; the script never chooses a GPU — on the shared cluster the scheduler
  does); `jax_default_device` is set to it so model and state live there too;
  configurations run **interleaved and repeated** (`--repeats`, min / median reported)
  after a multi-step warm-up; each step row reports **dispatch** (host loop returning)
  and **total** (device done) separately, so host- vs device-bound is read off directly;
  a **dispatch floor** (a trivial jitted function over the same state and batch pytrees)
  isolates the cost of handing arguments to JAX; a committed vs uncommitted
  device-resident pair separates "on the device" from "committed to the device";
  `--profile DIR` writes a `jax.profiler` trace of the `to_device` configuration.
- **Finding (CPU, reproducible here): grain's default reader threads slow the training
  loop.** Iterating a `MapDataset` directly — `windows(...).batch(B)` as the trainer's
  loader, or `to_iter_dataset()` with default `ReadOptions` — starts a 16-thread,
  500-element prefetch; those threads compete with the Python training loop for the
  GIL, and the step's host-side dispatch time goes from ≈15 ms (device-resident
  batches) to ≈90 ms, with `dispatch == total`, i.e. entirely host-bound. With a single
  reader thread (`ReadOptions(num_threads=1, prefetch_buffer_size=1)`) under
  `to_device`'s two prefetch stages, `to_device` drops to ≈22 ms per step — near the
  resident bound. This is why the first `to_device` row looked no better than NumPy
  batches. `data.single_threaded(dataset)` is the new helper; `to_device` uses it, and
  the `Evaluator` reads a grain dataset through it as well.
- `to_device(dataset, device)` — `device` is now a required argument (review: no
  auto-selection on a shared cluster); the notebook passes the card explicitly.
- Answers to the round-2 questions: `grain.experimental.device_put` creates exactly two
  `ThreadPrefetchIterDataset`s, one thread each (no pool) — the hidden threads were in
  *our* default `to_iter_dataset()`, now fixed; `with log, ckpt:` does replace the
  `ExitStack` (removed).

The V100 pattern itself (committed resident batches slowest) is not reproduced on CPU
(committed vs uncommitted differ 2× for the autoencoder here, not at all for the INN in
isolation) and awaits the dispatch/total/floor split from the redesigned script.

## Review round 2, part 2 (2026-10-04) — base classes instead of protocols

- **`Logger` and `Checkpointer` are abstract base classes** (`abc.ABC`), as the review
  asked: `log` / `save` are the abstract methods, `close()` is a concrete no-op, and
  `__enter__` / `__exit__` (exit calls `close`) live on the base class. The protocols and
  the two copies of `_Closing` are gone; every concrete logger and checkpointer now
  subclasses its base. The public names, `Trainer.train`'s signature and the tests are
  unchanged (`isinstance` checks by the beartype hook work on ABCs without
  `@runtime_checkable`). `__enter__` stays unannotated because the hook rejects
  `typing.Self` outside `@beartype`-decorated classes.
  - *Rejected*: `training/utils.py` holding a shared `_Closing` mixin next to the
    protocols (the review's alternative) — one more module, and the protocol would still
    have had to restate the context-manager methods the mixin provides.
- **ADR-0009 amended**: section 1 now says base classes, and records the reader-thread
  finding as a rule — the loop is host-sensitive, so a loader must not start grain's
  default reader pool; `single_threaded` / `to_device` are the sanctioned paths. The GPU
  outcome (committed vs uncommitted inputs, `mp_prefetch`) is left as an explicit
  placeholder until Joon's V100 run of `scripts/bench_dataloader.py --device <n>`.

**What the V100 run has to show.** The three rows that decide: if the *dispatch floor*
for committed batches is far above the uncommitted and NumPy floors, the slowness is the
host-side cost of handing committed arrays to a jitted function next to an uncommitted
state, and the fix is either committing the state at `init` (`jax.device_put(state,
device)`) or keeping loader batches uncommitted; if the floors agree and only *total*
differs, the device is doing extra work (a transfer per step) and the pipeline is the
place to look; if `to_device` ≈ resident ≈ floor, C7 closes with `to_device` and
`mp_prefetch` is judged by its own row.

## Review round 2, part 3 (2026-10-05) — the V100 numbers; C7 closed

`uv run python scripts/bench_dataloader.py --device 0` on a Tesla V100-SXM2-32GB; 512
trajectories × 120 steps, batch 512 × window 50, conjugacy model (8 blocks), 30 steps × 3
interleaved repeats (ms, min / median):

| Row | dispatch | total |
|---|---|---|
| fetch only (host) | 27.0 / 27.4 | |
| fetch only, `mp_prefetch(4)` | 7.4 / 8.9 | |
| dispatch floor: committed / uncommitted / NumPy batch | 0.8 / 0.7 / 0.8 | |
| step, device-resident, committed | 92.2 / 94.5 | 92.2 / 94.5 |
| step, device-resident, uncommitted | 88.9 / 92.7 | 88.9 / 92.7 |
| step, NumPy batches (option A) | 488.0 / 491.4 | 488.1 / 491.4 |
| step, `to_device` (option C) | 94.4 / 96.7 | 94.4 / 96.7 |
| step, `mp_prefetch(4)` + `to_device` | 464.3 / 471.2 | 464.3 / 471.2 |

What it settles:

- **The committed-input hypothesis is refuted.** All three dispatch floors are below 1 ms
  and committed and uncommitted resident batches step alike (92 vs 89 ms, within the
  repeat spread). The earlier "resident slowest" table was the old script's measurement
  artifact. Nothing to fix in `Trainer.init`.
- **C7 closes with `to_device`.** `to_device` costs 2 ms over device-resident batches: the
  single-reader prefetch thread hides the 27 ms fetch completely. `mp_prefetch` makes the
  fetch 3.6× faster in isolation and the step 5× slower end to end; NumPy batches in the
  loop are as bad. Both are out of the default pipeline (ADR-0009 §1 amended).
- **The step is host-bound with no data work at all** — dispatch ≈ total ≈ 92 ms with the
  batch already on the device, while the floor says a jitted call over the same pytrees
  returns in 0.8 ms. So the host spends ~90 ms *inside* `train_step` per call. Deduced,
  not yet measured: on the GPU backend the calling thread enqueues every kernel of the
  executable before the call returns (JAX's asynchronous dispatch is at the stream level),
  so a step made of many small serialized kernels is launch-bound — the host thread
  launching is the clock, and the device idles between launches. The Bautin closed-form
  flow fits that shape: every predicted point goes through `_radius_from_isostable`, a
  `fori_loop` of 64 bracket-expansion plus 48 Newton iterations (with `jax.grad` inside),
  serialized under `vmap` and differentiated in reverse, so one step is on the order of
  thousands of launches of 25 600-wide kernels. The alternative reading — the device is
  the bottleneck and the host is blocked by the in-flight-computation limit or by a sync
  inside the executable — gives the same dispatch ≈ total signature; the two are told
  apart by batch size: launch-bound dispatch is nearly flat in `--batch`, device-bound
  dispatch scales with it. The `--profile` trace shows it directly (kernel row dense with
  gaps vs saturated). This is a model/XLA item, not the loader's: proposed as roadmap C8.
- **The NumPy row was contaminated by grain's reader pool, not by the transfer.** That
  row iterated the `MapDataset` bare — the very 16-thread, 500-batch prefetch the round-2
  finding is about — next to the launch thread. Reproduced on CPU with the new rows:
  NumPy batches through `single_threaded` step in 20 ms, through the bare dataset in
  105 ms (5×; the V100 ratio was 4.7×). The row is now honest (`single_threaded`), an
  explicit `jax.device_put`-in-the-loop row is grain's option A literally, and the bare
  iteration stays as its own labeled row.
- **Why `mp_prefetch` is so slow** is not established; the fetch is fast, so the cost is
  on the main thread, and four worker processes competing with a host-bound launch thread
  for CPU on a scheduler-limited allocation is the plausible mechanism. The script now
  prints the process's CPU allowance (affinity, cgroup quota, `SLURM_CPUS_*`) in its
  header so the next run says.

**Second run, batch 512 vs 2048 (2026-10-05).** Resident batches: 90 → 122 ms for 4× the
points, i.e. ≈ 80 ms fixed + ≈ 10 ms per 512 points — the flat-in-batch signature of a
launch-bound step, with the device's own work a small fraction. Floors unchanged
(0.7–1.3 ms). Fetch scales linearly (26 → 104 ms; `mp_prefetch(4)` 7 → 22 ms). But
`to_device` no longer hides the fetch at 2048: 356 ms against 122 resident and 104 fetch,
more than the two *added* — the single fetch thread and the launch thread did not overlap
and interfered besides, and `mp_prefetch + to_device` went to 807 ms. Both point the same
way as the NumPy row: whatever else runs on the host — reader threads, a fetch thread with
104 ms of Python per batch, worker processes — slows the thread that launches the step,
far beyond time-sharing on a well-provisioned host. A one- or two-core allocation (a GPU
job's usual default) would produce exactly this; the header line decides it. The new
"to_device over cached batches" row (a pipeline with no fetch work) separates the fetch's
CPU from the thread mechanics directly.

**Diagnostics added to the script** (`--hlo-stats`): the compiled step is lowered and
its optimized HLO parsed — instruction count, every `while` with its `known_trip_count`
and launches per iteration, the number of `conditional` executions per step, and an
estimate of kernel launches per step; plus a micro-benchmark of a 2×2
`jax.scipy.linalg.expm` against the closed-form rotation.

**Third run, `--hlo-stats` (2026-10-05).** Host: 24 cores. Compiled step: 72 609 HLO
instructions, **114 while loops**, ≈ 15 400 launches per step; 88 ms / 15 400 ≈ 5.7 µs
per launch, the CUDA launch floor — launch-bound to the bone. The two root-solve loops
are 64 × 4 and 48 × 4; the other 112 loops are **16 iterations × 10 launches** each, and
16 is `jax.scipy.linalg.expm`'s `max_squarings`: `BiLipschitzLinear` builds its two
rotations with `expm(raw − rawᵀ)`, whose squaring step is a `scan` of 16 `lax.cond`s.
Two rotations × 8 layers × (`__call__` + `inverse`) × (primal + the Fréchet-derivative
`expm` of the custom JVP) ≈ 112. On the GPU backend a `conditional` needs its predicate
on the host, so each of those ≈ 1 800 conditionals per step is a device-to-host round
trip the launching thread waits for — at tens of µs each this *is* the ≈ 80 ms fixed
cost, and it is why the host can never run ahead of the device (dispatch ≈ total).
Deduced from the loop census and XLA's conditional lowering; the `expm` micro-benchmark
in `--hlo-stats` measures it directly on the V100.

The GIL, not CPU count, is what loader threads cost: with 24 cores the bare-dataset row
is still 4× the single-reader row (361 vs 94 ms), `mp_prefetch` likewise. A Python thread
slicing windows holds the GIL in 5 ms slices; the launching thread takes the GIL back
several times per step and waits behind every runnable Python thread each time (CPython's
GIL hand-off is not FIFO, so 16 readers mean many slices per wait). `to_device`'s single
prefetch thread costs 95 (min) to 121 (median) ms against 89 for the same pipeline with no
fetch work — acceptable at batch 512, and the cached-batches row is the control for it.

**Fix (C8), done in part 4 below** — the proposal was: replace `expm` in `BiLipschitzLinear`
by a loop-free orthogonal parameterization.

The script's reading hints were amended (dispatch ≈ total also means launch-bound or a sync
inside the executable, not only Python/GIL).

## Review round 2, part 4 (2026-10-05) — the fix: Cayley transforms (ADR-0010)

The mechanics behind parts 1–4 — asynchronous dispatch, committed/uncommitted arrays, the
GIL and grain's reader threads, what each row of the benchmark measures, the taxonomy of
bottlenecks and this case history — are written up for a reader new to JAX in
`docs/design/training-step-performance.md` (new, tentative until reviewed).

The fourth V100 run measured the suspect directly: `--hlo-stats` reported **1 696
conditional executions per step**, and a lone 2×2 `jax.scipy.linalg.expm` took **0.649 ms
per call** against **0.049 ms** for the closed-form rotation — 16 device-to-host round
trips of ≈ 40 µs. Joon: "let's resolve this now."

- `linear.cayley(skew)`: `Q = (I − A)(I + A)⁻¹`, written out for `dim = 2` (the rotation by
  `−2 arctan a`), one `jnp.linalg.solve` otherwise. Orthogonal with `det = +1` everywhere,
  `I` at zero (ADR-0002), always well conditioned; misses only rotations with an eigenvalue
  `−1`. `BiLipschitzLinear.constrain` uses it; docstrings updated. Why not Householder or
  a smaller `max_squarings`: ADR-0010.
- Tests: `test_rotations_have_no_conditionals[2, 3]` (compiled parameter map has no
  `conditional`; for `dim = 2` no `while`) and `test_cayley_dim2_closed_form_matches_the_solve`.
  The existing parameter-space laws (orthogonality, `det > 0`, singular values) pass
  unchanged, including at extreme raw values. Full suite: 447 passed, the known
  `circular_rq (K=8)` failure, one xfail.
- Loop census on CPU, 8 blocks: 114 → 3 `while` loops, ≈ 1 700 → 0 conditionals,
  ≈ 15 400 → ≈ 4 100 launches. Expected on the V100: the ≈ 70 ms of round trips gone, the
  step a few ms of launches plus the device's ≈ 10 ms per 512 points, and `dispatch` finally
  below `total`. To confirm: `uv run python scripts/bench_dataloader.py --device 0
  --hlo-stats --no-mp`; the number goes into ADR-0010's *Consequences*.
- Consequence to note: the raw-leaf-to-rotation map changed, so no checkpoint from before
  reproduces (none exist).

**Confirmation (V100, 2026-10-05).** Census: 2 `while` loops, 0 conditionals, ≈ 1 900
launches. Device-resident step **88 → 33 ms**; committed and uncommitted identical (33.4);
`to_device` over cached batches 33.4, so the prefetch thread itself costs nothing. Still
dispatch ≈ total: ≈ 17 µs per launch on the root solve's 448 loop iterations — launch-bound
on what is left, and nearly flat in batch size, so larger batches are the free lever.

**Now the fetch is the bound.** `to_device` (92.6) ≈ NumPy single reader (92.7) ≈ fetch only
(89.0): the one prefetch thread overlaps the 33 ms step with the 89 ms slice but cannot
produce batches faster than grain's per-element pipeline makes them — 0.17 ms per window
(`shuffle` → `random_map` with a per-element `np.random.Generator` → `batch`'s
`np.stack`). Before the fix this was invisible because the step itself took 88 ms. Measured
on the dev CPU: grain 50 ms per batch of 512 vs **0.85 ms** for one vectorized gather
(`ys[traj[:, None], start[:, None] + arange(L)]`) — proposed as roadmap C9: a batch-level
sampler with the same semantics (shuffled epochs, uniform / weighted / ranged starts,
mixing) producing whole batches, so training runs at the step's 33 ms.

## Review round 2, part 5 (2026-10-05) — the default device

Joon's round-2 review left two open thoughts, both about device choice: the benchmark's
`--device` is right not to grab a GPU on a shared node, but in an `srun` shell with one card
assigned it should run without the flag; and is `jax.devices()[0]` (tests, notebook) a
sensible default?

- **What JAX offers.** `jax.devices()[0]` *is* JAX's default device: the first device of the
  default backend ("generally `'gpu'` or `'tpu'` if available, otherwise `'cpu'`" — JAX,
  `jax.devices`), where uncommitted arrays and jitted computations land unless
  `jax_default_device` says otherwise (design document §2). So it is the right default
  *whenever the visible devices are the right ones* — on a CPU machine, in a job the
  scheduler scoped with `CUDA_VISIBLE_DEVICES` (Slurm's `--gpus`/`--gres` do), in tests. It
  is wrong only on a node where several accelerators are visible and nobody assigned one.
- **`data.resolve_device(index=None)`** encodes exactly that: an explicit index wins; one
  device visible, a CPU backend, or a `CUDA_`/`HIP_`/`ROCR_VISIBLE_DEVICES` variable set →
  `jax.devices()[0]`; several accelerators and no such variable → `ValueError` listing them
  and asking for the index. `scripts/bench_dataloader.py --device` is now optional and goes
  through it (the header says `--device` or `default`); the notebook calls `resolve_device()`
  and passes the result to both `jax_default_device` and `to_device` (its `to_device` call
  had in fact been left without the device argument — fixed). Tests keep
  `jax.devices()[0]`, which on CPU is what `resolve_device()` returns;
  `test_resolve_device_*` cover the explicit, CPU-default and refusal paths (the fakes cannot
  pass the return annotation's runtime check, so the scheduler-scoped branch is covered by
  the one-device case).
- *Rejected*: making `to_device`'s `device` optional with the same resolution inside. The
  library function stays explicit (ADR-0009 §1); the policy lives in one named place a
  script calls once, so a reader of a training script sees where the device came from.

## C9 (2026-10-05) — the batched window source

Decided with Joon in discussion (the transform/source distinction, the concrete length,
`num_steps` on the data): ADR-0008 Decision 3 has the decision and the rejected shapes.

- **`data.WindowBatchSource(source, length, batch, *, seed, epochs, weight | start_range |
  ranges + range_weights)`** — a `RandomAccessDataSource` whose element `i` is the `i`-th
  batch of the run: `e, j = divmod(i, batches_per_epoch)`; in the uniform mode the `j`-th
  slice of `permutation(num_windows, rng=[seed, e])` decoded by `divmod(id, hi − lo)` into
  `(trajectory, start)`; in the weighted/mixed modes `num_windows` draws per epoch with
  replacement (`rng=[seed, e, j]`; inverse-CDF on the weight, or a Bernoulli between two
  ranges). One gather `ys[traj[:, None], start[:, None] + arange(L)]`; `t` from the shared
  grid. `len = epochs · batches_per_epoch`, `batches_per_epoch = num_windows // batch`
  (remainder dropped; error if zero). Picklable (the permutation cache is dropped on
  pickling) — `mp_prefetch` still works. `for_steps(n)` sets `epochs = ceil(n /
  batches_per_epoch)`.
- **`window_batches(source, length, batch, *, seed, epochs= | num_steps=, weight=,
  start_range=)`** and **`mixed_window_batches(..., split_idx, weights=, seed, epochs= |
  num_steps=)`** return `grain.MapDataset.source(...)`; the training pipeline is
  `to_device(window_batches(...), device)` — no `shuffle`, `repeat`, `random_map` or
  `batch` nodes. Resume at step `s`: `window_batches(...)[s:]`.
- **`Trainer.train(num_steps=None)`**: `None` runs the loader to its end (the normal call
  with a finite loader); a given `num_steps` is an upper bound and a loader ending first
  now warns (`UserWarning: the loader ended after 7 of 100 steps`) instead of stopping
  silently. `itertools.count()` replaces `range(num_steps)`.
- `windows`/`mixed_windows`/`RandomWindow`/`WeightedWindow` unchanged — the per-element
  reference; `validation_windows` unchanged.
- Measured (dev CPU, batch 512 × 50): fetch **0.6 ms** per batch against 49 for
  `windows(...).batch(512)` — the benchmark's new "fetch only, per-element
  windows().batch()" row keeps the comparison; the `to_device` row should now sit at the
  step on the V100.
- **V100 confirmation (2026-10-05, batch 512 × 50, 8 blocks).** Fetch **0.7 ms** per batch
  (per-element `windows().batch()`: 88.5). `to_device` **32.6 ms** per step against 31.0
  device-resident, cached-batches 32.4, NumPy single reader 32.0, explicit `device_put`
  32.5 — every loader within 2 ms of the step, so the loader is no longer measurable; even
  grain's 16 default readers cost only 3.7 ms now that each element is a 0.7 ms batch. Day
  total: the training loop went from ≈ 93 ms per step (88 step + fetch exposed) to 33 ms.
  What remains is the step itself, launch-bound (dispatch ≈ total, ≈ 1 900 launches at
  ≈ 16 µs, the two root-solve loops 448 of them) and nearly flat in batch size — larger
  batches, then `unroll`/fewer root iterations, are the Phase D levers.
- Callers: `scripts/bench_dataloader.py` (`pipeline()` is `window_batches(..., epochs=1000)`,
  the per-element pipeline kept as a fetch row); `prototype.ipynb` (`mixed_window_batches(…,
  num_steps=2500)`, `train` without `num_steps`).
- Tests (`tests/test_data.py`, 6 new): shapes/dtype and contiguity of every window;
  two-pass determinism and seed dependence; an epoch is every window exactly once and the
  next epoch is a reshuffle of the same set; remainder dropping and the too-large-batch
  error; `start_range` respected, weighted frequencies match the weights (same law as
  `WeightedWindow`), mixed early/late ratio, argument validation; `num_steps` → `len`,
  slicing equals indexing, pickle round trip; through `to_device` on the default device.
  `tests/test_training.py`: `num_steps=None` runs to the end without a warning; the
  exhausted-loader test now asserts the warning.

## Design

The decisions and rejected alternatives are ADR-0009. Points specific to this branch:

- **Why the delayed logging stayed** (Joon asked for the evidence). JAX returns from a
  jitted call before the computation runs; reading a metric blocks until it is done. The
  cookbook logs the *previous* step's metrics after enqueueing the current one, so the
  device never waits on the host. The host-side work that would otherwise sit in the
  bubble is the data fetch: our `windows(...).batch(128)` costs **15 ms per batch** (pure
  Python window slicing under the GIL; grain's 16 reader threads do not help, 14.7 ms;
  `mp_prefetch` failed to pickle the source in the dev container — roadmap C7). On CPU all
  logging variants measured 38 ms/step (nothing to overlap); on a GPU with a few-ms step
  the delay hides the fetch. Cost of keeping it as an adapter: zero in the loop body.
- **`default_weights` is `init=True`.** ADR-0004 asks for `init=False` static fields for
  `AbstractVar`s, but equinox warns about float leaves in `init=False` fields
  (`_MSG_FIELD_INIT_FALSE`); a tuple of floats is one. An instance may now override the
  defaults, which is useful anyway.
- **`Logger`/`Checkpointer` were `@runtime_checkable` protocols** until round 2 because
  the beartype import hook checks parameter annotations with `isinstance`; they are now
  abstract base classes (round 2, part 2), which `isinstance` handles natively.
- **`BestN` direction.** Orbax's `BestN(reverse=False)` sorts ascending and keeps the
  *last* `n`, i.e. the largest metric; minimization needs `reverse=True`. Found by the
  round-trip test (step 5 with `val/mse = 3.0` was kept instead of step 10 with `1.0`).
- **Restoring with sharding.** The abstract state passes each leaf's `sharding` into its
  `ShapeDtypeStruct`; without it Orbax warns and reads sharding from the file.
- **`Evaluator` iterates a finite, deterministic dataset to exhaustion** on every call
  (`validation_windows(...).batch(B)`; round 1 — the initial version collected `n`
  batches once), so every evaluation sees the same windows and the comparison across
  steps is meaningful; the bounding-box grid is derived from a first pass.
- **Trainer loop never reads device values**: the step counter is a Python `int`, the
  float conversion happens in loggers (`to_floats`) and in `evaluate`'s return.

## Bugs fixed

- **Importing the package initialized a JAX backend.** Module-level constraint
  primitives (`A_CONSTRAINT`, `B_CONSTRAINT`, `DECAY_CONSTRAINT`) computed their
  identity-at-zero shift with `jnp` at construction, so `import deep_isochron.data`
  initialized JAX. Symptom (Joon's V100 run of `scripts/bench_dataloader.py`): every
  grain `mp_prefetch` worker re-imports the package to unpickle the source, each
  initialized CUDA and tried to preallocate 75 % of a GPU the parent already held, and all
  died with `CUDA_ERROR_OUT_OF_MEMORY` cascades (9.22 GiB → 18 MiB retries). The shift is
  now a `functools.cached_property` computed on first use (ADR-0005 amended in spirit:
  primitives stay plain objects; nothing JAX runs at import).
  `test_importing_the_package_does_not_initialize_a_jax_backend` pins it (subprocess).
  The benchmark script additionally sets `JAX_PLATFORMS=cpu` when it runs as a spawned
  worker (`__name__ == "__mp_main__"`), belt and braces.

- `ConjugacyTrajectoryLoss` averaged the squared error over coordinates as well as batch
  and time (a factor `dim` relative to the squared Euclidean norm the autoencoder loss
  used). Both now use `trajectory_mse` = mean over batch and time of `‖·‖²`.
- The previous trainer saved only the model's weights, so a run could not resume, and
  selected the "best" checkpoint on the training loss of the *previous* step.
